## Correcciones realizadas

### 1. Contador de segundos real en los pasos del pipeline

**Problema:** El componente `StepBox` iniciaba su cronómetro local (`startRef.current = Date.now()`)
al montarse. Como el detalle de una fila se monta recién al expandirla, colapsar y volver a
abrir la fila reiniciaba el contador desde cero aunque el proceso llevara minutos corriendo.

**Solución:** Se añadieron cuatro campos de marca de tiempo a `RowData`:
`nluStartedAt`, `visualStartedAt`, `bitmapStartedAt`, `structuredSvgStartedAt` (tipo `number`,
milisegundos epoch). Se asignan en `processStep` y `processCascade` cuando cada paso entra en
`processing`, y se borran al completar o fallar. `StepBox` recibe `startedAt?: number` como prop
y calcula `elapsed = (Date.now() - startedAt) / 1000` directamente, sobreviviendo ciclos de
colapso/expansión.

Archivos: `types.ts`, `App.tsx` (`processStep`, `processCascade`, `StepBox`, `RowComponent`).

---

### 2. Estado "processing" fantasma al recargar la página

**Problema:** `sanitizeRow` aceptaba `'processing'` como estado válido. Si el navegador se
cerraba mientras una fila procesaba, al reabrir la app las filas aparecían con el spinner
naranja palpitante pero sin ningún runner activo.

**Solución:** En `sanitizeRow` (`services/rowSerialization.ts`):
- `status: 'processing'` → `'error'` (el proceso no terminó).
- `nluStatus / visualStatus / bitmapStatus / structuredSvgStatus: 'processing'` → `'idle'`.
- Los campos `*StartedAt` se eliminan en la hidratación (son runtime-only).

Archivo: `services/rowSerialization.ts`.

---

### 3. Mensajes de error del proveedor más explícitos

**Problema:** Los bloques `catch` en `processStep` y `processCascade` registraban solo
`err.message`, perdiendo el proveedor, el código HTTP y el requestId.

**Solución:** Se añadió `formatProviderError(err)` junto a `processCascade` en `App.tsx`.
- `ExternalProviderQuotaError` → `"Cuota del proveedor agotada — provider=X, model=Y, ref=Z, retry-after=Ns"`
- `ProviderRequestError` → `"Error del proveedor HTTP 4XX [reintentable] — ...; provider=X; fuente=Y; ref=Z"`
- Cualquier otro error → `err.message`.

Se importó `ProviderRequestError` desde `./services/aiClient`.

Archivo: `App.tsx`.

---

### 4. Alias `PICTOS_OPENAI_KEY` en `.env` local

**Problema:** Netlify CLI v24 sobrescribe `OPENAI_API_KEY` con un JWT de AI Gateway al
inyectar las variables del sitio enlazado (producción `24f068d3`), exactamente igual a lo que
ocurrió antes con `ANTHROPIC_API_KEY`. Los workers de background invocaban a OpenAI con el
JWT en lugar del API key real, obteniendo `401: invalid_issuer`.

**Diagnóstico:** La clave local en `.env` funciona perfectamente (`GET /v1/models/gpt-image-2`
→ 200, generación directa → 200). El worker fallaba porque Netlify dev inyectaba la variable
del sitio encima de `.env`.

**Solución:** Se añadió `PICTOS_OPENAI_KEY` a `.env` con el mismo valor que `OPENAI_API_KEY`.
`openaiApiKey()` en `_shared/openaiImage.js` consulta `PICTOS_OPENAI_KEY` primero, por lo que
no puede ser sobreescrita por Netlify dev.

Archivo: `.env` (no versionado).

### 5. Race condition en carga de bitmaps desde IndexedDB

**Problema:** Al abrir una librería, los pictogramas aparecían en blanco con frecuencia.
El flujo de `openLibrary` llama a `flushPendingSave()` (síncrono), que dispara
`saveBitmapsBatch` (asíncrono: compresión PNG con canvas + escritura IDB). Inmediatamente
después, `getAllBitmapsForLibrary` lanzaba la consulta de lectura. La lectura completaba
antes de que la transacción de escritura se confirmara en IDB → mapa vacío → la
recuperación de plantilla fallaba silenciosamente para librerías generadas por el usuario
→ pictogramas en blanco.

**Diagnóstico:** Race condition entre el write (async, compression + IDB commit) y el read
(async, pero sin esperar al write anterior). Afectaba principalmente a bitmaps PNG grandes
y a cierres/reaperturas rápidas de librerías.

**Solución:** Se añadió `pendingBitmapWriteRef` (`useRef<Promise<void>>(Promise.resolve())`)
que almacena la Promise activa de `saveBitmapsBatch`. En `openLibrary`, la lectura de IDB
se encadena detrás de esa Promise:

```
Promise.all([
  pendingBitmapWriteRef.current.then(() => IndexedDBService.getAllBitmapsForLibrary(id)),
  IndexedDBService.getAllSvgsForLibrary(id),
])
```

Tres cambios en `App.tsx`: declaración del ref, asignación al llamar `saveBitmapsBatch`,
y encadenamiento en `openLibrary`. TypeScript limpio.

Archivo: `App.tsx`.
